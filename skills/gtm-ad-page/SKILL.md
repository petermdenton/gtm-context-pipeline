# Ad to landing page

Read checkout `AGENTS.md`, the client brand/claim evidence, the actual supplied
creative and [authoring guidance](references/authoring.md). Determine whether
the request is a brief, implemented local page, existing-route edit or separate
variant. Resolve the audience, promise, CTA, destination and source versions.
Do not regenerate a supplied ad simply to create its page.

The portal's Landing pages tab stores draft text/reference links. It does not
render a website or publish a destination. For a requested page implementation,
inspect the user's chosen destination project/template or build an appropriate
local artifact within scope. Keep new client page sources under a private run
unless the user supplied another authorized destination. A reusable renderer
belongs in this toolkit only when implementation is part of the request.

Use actual product evidence, approved claims and provided brand assets. Label
mockups/demo data and do not present generated UI as a real screenshot. Connect
the ad promise to inspectable behavior with concise copy and a suitable CTA.
Do not impose another company's SDK, page sections, screenshots or CTA pair.

Respect the requested route treatment. Keep a separate variant's actual path
and preserve its canonical page. If an existing destination is supplied and no
variant is requested, update that destination and state the assumption. A new
audience needs an appropriate destination, not a relabeled unrelated cluster.

Pin page/context/creative versions and the experiment or treatment hypothesis.
Record input hashes, evidence, audience, metric, denominator and window in the
private handoff. Keep editorial review, local rendering, publication and launch
separate. No experiment, freeze, campaign build or publish CLI is provided here.

For implemented pages, verify rendering, responsive layout, keyboard behavior,
assets and CTA destinations. Inspect the actual page at desktop/mobile sizes.
Use the destination's build/test tools when they exist. A static preview does
not verify server access control or event ingestion. Report tracking as planned,
implemented or verified according to evidence, not an assumed collector.

If publication is requested or already authorized, use the destination's verified
owning publisher and preserve its assets, handlers, bindings and rollback path.
The source project's deployment is not a default destination. With no supported
publisher, finish the local page and report that specific deployment gap.

Deliver the actual brief/page and preview method, source files, route, version
links, rationale, checks and publication state. Hand operations the verified
destination and tracking configuration; page creation does not launch ads.
