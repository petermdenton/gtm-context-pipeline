# Platform actions and feedback

## Read engagement

Use the user-selected client/account and reporting view. Record account, actual
window, timezone, filters, segment definitions, capture time and pagination.
Preserve company IDs, available metrics and suppressed values. Keep platform
labels separate from fit. See the outreach
[network handoff](../../gtm-outreach/references/network-handoff.md) only when
the task includes relationship paths or buyer research.

Company-level platform attribution does not identify the person who engaged.
Account-wide metrics do not establish which campaign caused them. Inspect
employment scope, expansion and exposure before interpreting unexpected accounts.
Rolling-window deltas are not necessarily yesterday's activity. Keep missing
coverage distinct from no recorded activity.

## Resolve the requested change

Map reviewed audience/version to the actual client ad account, campaign/adset,
targeting mechanism, existing selections, buyer/geography filters, exclusions,
employment scope, expansion, creative IDs, destinations, budget and status.
Resolve company identities by corroborated IDs/domain, not similar names.
Do not impose a source project's platform or targeting mode.

Produce an exact delta of additions, already-present records, holds and any
requested removals. Refresh relevant customer/suppression evidence. Preserve
unrelated filters and existing selections. Check current supported provider
tools, authentication and platform rules before choosing API or browser work.

Reuse established authorization. Adding selected companies does not authorize
changing budgets, launching, removing other audiences or sending messages.
Finish the reviewable delta before asking for genuinely missing scope/input.
A skills-editing request authorizes none of these external actions.

## Apply and verify within scope

1. Save the current settings privately. Re-read the baseline before mutation
   when another operator may have changed it; reconcile conflicting changes.
2. Apply only the authorized delta with supported tools. Preserve targeting
   logic, exclusions, expansion, geography, roles, budgets, status and schedules
   unless the requested change includes them. An edit to a running audience is
   a live mutation even if launch status stays unchanged.
3. Inspect platform validation, save and read back the result. Record per item
   `verified-added`, `already-present`, `held`, `failed` or `verification-pending`
   with observed evidence. Verify preserved settings too.
4. If save results are ambiguous, inspect the live state before retrying only
   missing authorized work. Stop the affected action at access failures,
   conflicting settings or unresolved results. Never blindly repeat saves.

Keep mappings, screenshots, before/after state and action journals under the
private run. Use stable batch/item keys to avoid duplicates. Recovery must not
overwrite later operator changes with an old full snapshot.

For new campaign setup, prepare reviewed assets, real destination, targeting,
suppression, reach, owner, currency, budget, bids, schedule and measurement plan.
Setup does not imply activation. After an authorized launch, read back status
and distinguish configured, enabled and observed delivery. Publication stays
with the destination's owning publisher.

## Review and resume

Carry batch/seed IDs, verified addition times, taxonomy and creative/page versions
into readouts. Report overlaps, prior exposure and attribution gaps. Combine
platform, website and sales evidence only where supported; impressions are not
qualification and missing delivery is not rejection.

Return fit hypotheses to clusters, message findings to authoring/pages and
verified sales outcomes to outreach. Preserve original hypotheses and negative
evidence. For requested recurring work, define cadence, destinations, limits,
review rules, authorization, verification and stop conditions, then use the
actual scheduling tool. A written plan is not an active automation.
